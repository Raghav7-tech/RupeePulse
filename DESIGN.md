# RupeePulse — Product & Engineering Plan

## Challenge, restated

Build a frontend-only, consumer-grade finance website for an Indian Gen Z user managing ₹10,000 across 30 days. The product must make trade-offs tangible: every expense, income, cancellation, goal change, or surprise should ripple through balance, safe daily spend, forecast, goal confidence, risk, and financial health. The decision simulator is the product's centre of gravity.

## Assumptions

- Desktop is the primary judging viewport, with complete responsive behaviour down to 360px.
- The evaluator should land directly in a realistic demo rather than face an onboarding wall; onboarding remains accessible from Reset.
- All state is local and deterministic. There is no auth, backend, or remote data dependency.
- The provided Stitch exports are visual references, not production code. The implementation is original React + TypeScript.
- Aarav is a 21-year-old design intern in Bengaluru with a ₹10,000 monthly allowance, an expected ₹1,500 freelance payment, fixed commitments, a Goa goal, and a small emergency buffer.

## Core loop

1. Read today's money state and the reason behind each metric.
2. Ask “what if?” and preview a decision without mutating reality.
3. Inspect the before/after ripple across six linked outcomes.
4. Commit or discard.
5. Advance time; scheduled cashflow and surprise events resolve.
6. Adapt spending, subscriptions, and goals to finish the month solvent.

## Information architecture

- **Today** — command centre, quick-add ledger, upcoming shock, goals, subscriptions.
- **Simulator** — presets and custom decisions, before/after comparison, ripple chain, verdict.
- **Forecast** — expected/best/worst cashflow, schedule, risk drivers, health breakdown.
- **Plans** — subscriptions, commitments, savings goals, efficiency and cancellation simulations.
- Global controls: day advance, auto-run, theme, reset, command palette/mobile menu.

## State model

- `Transaction`: id, day, title, amount, kind, category.
- `Income`: id, title, amount, day, paid.
- `Commitment`: id, title, amount, day, paid, essential.
- `Subscription`: id, title, amount, day, active, worthIt.
- `SavingsGoal`: id, title, target, saved, deadlineDay, priority.
- `UnexpectedEvent`: id, day, title, amount, handled.
- `FinanceState`: day, budget, opening balance, buffer, all collections.
- `Decision`: one-time expense/income, cancel/add subscription, goal contribution, event handling.

## Financial engine

All computed data is generated by pure functions in `src/engine/engine.ts`.

- **Balance** = opening budget + realised income − realised expenses − paid scheduled outflows − goal contributions.
- **Committed outflow remaining** = unpaid commitments + active subscriptions due + required remaining goal contribution within this cycle.
- **Safe daily allowance** = max(0, balance + expected income − committed outflow − emergency buffer) ÷ remaining days. A non-positive pool becomes “Overspent”, never a negative allowance.
- **Forecast** = day-by-day cash position using recent average discretionary burn, scheduled income/outflows, and a probability-weighted surprise reserve. Best/expected/worst vary the discretionary burn and shock assumptions.
- **Runway** = balance ÷ current daily burn, capped for display at the days remaining.
- **Risk (0–100)** = runway pressure (35%), projected deficit (25%), buffer coverage (20%), committed share (10%), shock exposure (10%). Levels: Low < 25, Moderate < 50, High < 75, Critical ≥ 75.
- **Health (0–100)** = budget adherence (25%), savings progress (20%), buffer coverage (15%), subscription efficiency (15%), essential/discretionary mix (15%), consistency (10%).
- `simulate(state, decision)` clones state, applies the decision, and recomputes all metrics to return `{before, after, delta, nextState}`.

## UX direction

Obsidian surfaces, crisp Outfit/Inter-like typography, neon mint for action and progress, indigo for forecast context, and coral/amber only for risk. Cards use subtle tonal elevation instead of noisy glass. Motion communicates recalculation; it never blocks action and is disabled under `prefers-reduced-motion`.

## Scope cut-list

If time is constrained, preserve in this order: single engine, simulator, dashboard, quick-add, forecast, day advance/events, plans, persistence, responsiveness. Nice-to-have items such as full onboarding forms, share-image export, and elaborate achievements are cut before core causality.

## Six-hour build sequence

1. Plan, scaffold, tokens, seed model.
2. Pure engine and tests.
3. Shared store, shell, dashboard, quick-add, time travel.
4. Simulator and ripple verdict.
5. Forecast, plans, risk/health insights.
6. Responsive, accessibility, persistence, QA, README.
